# Прямая доставка музыкального дневника в конкретный чат ChatGPT

**Статус:** обязательное требование релиза 1.0; найден официальный технический механизм, но доступность для личного Plus-аккаунта и возможность использовать именно существующий чат ещё нужно подтвердить.  
**Актуализировано:** 26 ноября 2026 года.

## Требование Кати

События музыкального дневника должны автоматически поступать **в один конкретный чат ChatGPT**, предназначенный для обсуждения музыки.

Не подходят:
- создание нового чата на каждую отправку;
- запись только в файл, Google Drive или внутреннюю почту «Чанти Моста»;
- ручное копирование/вставка или ручная пересылка;
- доставка музыкальных событий в чат «Миры Магира».

После однократной настройки маршрута обычное прослушивание не должно требовать дополнительных действий.

## Что уже есть в коде приложения

- `MusicListenerService` получает Android MediaSession и уведомления поддерживаемых плееров.
- `MediaScan` отбирает Яндекс Музыку и выбранные видеоплееры.
- `TrackStore` локально хранит начало/смену трека, паузу/возобновление, длительность и рейтинг только при наличии реального события рейтинга.
- `VideoStore` хранит доступные метаданные видео, не считывая видеоряд.
- `MainActivity.copyDiary()` сейчас только собирает текст, кладёт его в буфер обмена и предлагает открыть ChatGPT. `openChat()` запускает приложение ChatGPT или общий сайт, но не конкретный диалог.

Следовательно, сбор событий уже существует, а автоматическая доставка в целевой диалог отсутствует.

## Что найдено в «Чанти Мосте 1.0/1.1»

В таблице есть активные маршруты проекта `music` и получателя `music` («Чанти — музыка»). Это подходящие внутренние обозначения маршрута, но не идентификатор конкретного диалога ChatGPT.

Текущая внешняя интеграция Алисы ограничена в Apps Script агентом `alice` и проектом `general`; Cloudflare Worker также отправляет события с этими значениями. Готового маршрута Android-приложения к получателю `music` пока нет.

Внутренняя запись в таблицу «Почта» моста сама по себе не считается выполнением требования Кати: это лишь транспорт/очередь, а не сообщение в целевом чате.

## Новый официальный механизм OpenAI: MCP Events

В документации OpenAI обнаружен механизм MCP Events:
- он доступен в Work-чатах ChatGPT Web, в Work-чатах настольного приложения при выборе Cloud, а также в Dots;
- MCP-сервер объявляет события через `events/list`;
- когда пользователь просит подписаться, ChatGPT вызывает `events/subscribe` и передаёт серверу callback URL и signing secret;
- сервер сохраняет подписку и отправляет события на этот callback как подписанные Standard Webhooks;
- OpenAI указывает, что ChatGPT получает событие **в подписанном чате** и действует по заданным пользователем инструкциям.

Это именно тот тип push-доставки, который технически может направить событие в конкретный подписанный Work-чат. Это не Conversations API и не создание отдельной API-беседы.

Документация:
- https://developers.openai.com/plugins/build/mcp-events

## Ограничения доступа и открытые вопросы

1. **План ChatGPT.** Справка OpenAI указывает, что частные custom MCP connections и полный MCP доступны Business и Enterprise/Edu; Pro может подключать custom MCP-серверы с read/fetch-разрешениями. Plus не указан среди планов с частным custom MCP-подключением. Публичный каталог плагинов доступен шире, но для собственного удалённого MCP-плагина требуется пройти публикацию и проверку OpenAI.
2. **Тип чата.** MCP Events поддерживается в Work-чатах. Документация описывает создание Work-чата и подписку в нём, но не подтверждает, что обычный существующий Chat-диалог можно преобразовать в Work без создания нового.
3. **Публикация плагина.** Для публичной публикации требуются верификация разработчика, публичные HTTPS-страницы сайта/поддержки/политики конфиденциальности/условий, доменная проверка, тестовые сценарии и проверка OpenAI. Публичный плагин сможет быть доступен другим пользователям; изоляция данных должна быть обеспечена авторизацией и отдельными токенами.
4. **API Conversations.** `POST /v1/conversations/{conversation_id}/items` добавляет items в API-managed conversation. Документация не связывает этот ID с существующим чатом из пользовательской истории ChatGPT; поэтому этот API не считается решением задачи Кати.

## Предварительная архитектура, если доступ подтвердится

`Android MediaSession → локальная очередь приложения → Chanti Bridge/Cloudflare Worker → MCP Events server → подписанный callback ChatGPT → один целевой Work-чат`

MCP-сервер должен:
- поддерживать Streamable HTTP и `events/list`, `events/subscribe`, `events/unsubscribe`;
- хранить подписку, callback URL, secret, срок действия и cursor в устойчивом хранилище;
- проверять callback challenge и отправлять подписанные Standard Webhooks;
- сохранять стабильный eventId при повторах, повторять временные ошибки с backoff, не создавать дубликаты;
- принимать только события маршрута `music`, не смешивая их с `magir`;
- предоставлять явный способ привязать устройство и отозвать его токен.

Android-приложение не должно содержать OpenAI API key, ChatGPT session token или секрет callback. Секреты хранятся на сервере.

## Критерии приёмки

- Маршрут привязан к одному конкретному чату; он не меняется сам.
- Новые события появляются именно в этом диалоге как сообщения, доступные Чанти для обсуждения.
- Не создаются новые чаты на каждое событие и не требуется ручное копирование.
- Повторная доставка не создаёт дубликаты; при отсутствии сети события сохраняются и отправляются после восстановления связи.
- Музыка и «Миры Магира» имеют независимые адресаты и очереди.
- Система честно сообщает о доставке/ошибке; «принято мостом» не выдаётся за «появилось в чате».
- До успешного теста на реальном целевом чате функция не считается готовой, а релиз 1.0 не объявляется полностью соответствующим требованию.
