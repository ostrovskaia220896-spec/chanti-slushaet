# Прямая доставка музыкального дневника в конкретный чат ChatGPT

**Статус:** требование Кати — автоматическая доставка в один конкретный существующий обычный чат ChatGPT. По состоянию на 26.11.2026 документированного официального способа для обычного Chat не найдено. MCP Events — возможный маршрут только через Work-чат и не сохраняет идентичность исходного разговора.  
**Актуализировано:** 26 ноября 2026 года.

## Требование Кати

События музыкального дневника должны автоматически поступать **в один конкретный уже существующий чат ChatGPT**, предназначенный для обсуждения музыки. Катя уточнила 26.11.2026: это обычный Chat, не Work.

Не подходят:
- создание нового чата на каждую отправку;
- запись только в файл, Google Drive или внутреннюю почту «Чанти Моста»;
- ручное копирование/вставка или ручная пересылка;
- доставка музыкальных событий в чат «Миры Магира»;
- подмена исходного обычного разговора новым Work-чатом без согласия Кати.

После однократной настройки маршрута обычное прослушивание не должно требовать дополнительных действий.

## Что уже есть в коде приложения

- `MusicListenerService` получает Android MediaSession и уведомления поддерживаемых плееров.
- `MediaScan` отбирает Яндекс Музыку и выбранные видеоплееры.
- `TrackStore` локально хранит начало/смену трека, паузу/возобновление, длительность и рейтинг только при наличии реального события рейтинга.
- `VideoStore` хранит доступные метаданные видео, не считывая видеоряд.
- `MainActivity.copyDiary()` сейчас только собирает текст, кладёт его в буфер обмена и предлагает открыть ChatGPT. `openChat()` запускает приложение ChatGPT или общий сайт, но не конкретный диалог.

Следовательно, сбор событий уже существует, а автоматическая доставка в целевой диалог отсутствует.

## Что найдено в «Чанти Мосте 1.0/1.1»

В таблице есть активные маршруты проекта `music` и получателя `music` («Чанти — музыка»). Это подходящие внутренние обозначения маршрута, но не идентификатор конкретного диалога ChatGPT.

Текущая внешняя интеграция Алисы ограничена в Apps Script агентом `alice` и проектом `general`; Cloudflare Worker также отправляет события с этими значениями. Готового маршрута Android-приложения к получателю `music` пока нет.

Внутренняя запись в таблицу «Почта» моста сама по себе не считается выполнением требования Кати: это лишь транспорт/очередь, а не сообщение в целевом чате.

## Проверенные официальные возможности OpenAI

### 1. MCP Events — только Work-чаты

Официальная документация OpenAI прямо указывает, что MCP Events доступны в Work-чатах ChatGPT Web, в Work-чатах настольного приложения при выборе Cloud, а также в Dots. Протокол позволяет MCP-серверу перечислить события, принять `events/subscribe` с callback URL и signing secret, а затем отправлять подписанные webhook-события. ChatGPT получает событие **в подписанном чате**.

Однако инструкция по тестированию требует начать чат и подписаться на событие; документация Work описывает запуск нового Work-чата или Work-чата из существующего Project. Официально документированного способа превратить существующий обычный Chat в Work-чат не найдено. Следовательно, MCP Events не доставит события в исходный обычный музыкальный чат Кати.

Источники:
- https://developers.openai.com/plugins/build/mcp-events
- https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex

### 2. Планы и подключение MCP

Справка OpenAI указывает, что частные custom MCP connections и полный MCP доступны ChatGPT Business и Enterprise/Edu. Pro может подключать custom MCP с read/fetch permissions; Plus не указан как тариф, позволяющий напрямую создавать собственное частное MCP-подключение.

При этом публичный Plugin Directory доступен на разных тарифах, хотя доступность конкретного плагина и его функций зависит от плана, рабочей области и реализации. Поэтому потенциальный путь для личного Plus-аккаунта — публикация нашего MCP-плагина в публичном каталоге и проверка его доступности/поддержки MCP Events в Work. Это не готовое решение: публикация требует верификации разработчика, публичного HTTPS endpoint, страниц сайта/поддержки/политики конфиденциальности/условий, тестовых сценариев и ревью OpenAI. Портал публикации поддерживает OAuth или отсутствие аутентификации; API-key/Bearer token flow через портал не поддерживается.

Источники:
- https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt
- https://help.openai.com/en/articles/20001256-plugins-in-chatgpt
- https://developers.openai.com/plugins/deploy/submission

### 3. Проекты — можно сохранить контекст, но не идентичность диалога

ChatGPT позволяет переместить существующий обычный чат в Project. Work можно запустить из Project, используя контекст проекта. Это потенциально позволит новому постоянному Work-чату опираться на историю музыкального дневника, если исходный чат будет перенесён в Project и доступен как контекст.

Но Work-чат останется отдельным разговором. События не будут появляться в исходном обычном чате. Это только вариант миграции контекста и возможный компромисс, который Катя должна отдельно одобрить.

Источник:
- https://help.openai.com/en/articles/10169521-projects-in-chatgpt

### 4. API Conversations

`POST /v1/conversations/{conversation_id}/items` добавляет items в API-managed conversation. Документация не связывает этот ID с существующим чатом из пользовательской истории ChatGPT; поэтому этот API не считается решением задачи Кати.

Источник:
- https://developers.openai.com/api/reference/resources/conversations/subresources/items/methods/create

### 5. Work event-triggered tasks

В актуальной справке ChatGPT Work webhook-based event-triggered tasks описаны для поддерживаемых приложений Gmail, Slack и GitHub. Это не документирует произвольный webhook от «Чанти Моста» в существующий обычный Chat. И сами такие задачи работают в Work.

Источник:
- https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex

## Вывод

**Для исходного обычного чата Кати подтверждённого официального автоматического push-механизма нет.** Не следует выдавать MCP Events, API Conversations, внутреннюю почту моста, Gmail-уведомление или запуск ChatGPT за прямую доставку в этот диалог.

Реальные варианты:
1. Сохранить исходный обычный чат и продолжить ручную вставку дневника — не соответствует автоматизации.
2. Если Катя согласится, переместить исходный чат в Project и создать один постоянный Work-чат с контекстом проекта; изучить публикацию публичного MCP-плагина и проверить MCP Events на её тарифе. Это отдельный Work-чат, а не тот же разговор.
3. Продолжить исследование официального механизма доставки именно в обычный Chat. Пока такого API в публичной документации не найдено; не использовать внутренние API приложения ChatGPT, извлечение его токенов или обход защиты.

## Предварительная архитектура для варианта 2 (не утверждена)

`Android MediaSession → локальная очередь приложения → Chanti Bridge/Cloudflare Worker → MCP Events server → подписанный callback ChatGPT → один постоянный Work-чат`

MCP-сервер должен поддерживать `events/list`, `events/subscribe`, `events/unsubscribe`, устойчивое хранение подписок, callback verification, подписанные Standard Webhooks, дедупликацию по eventId, повторы с backoff, раздельные маршруты `music` и `magir`. Секреты callback и серверные токены не помещать в Android APK.

## Критерии приёмки

- Для исходного требования: событие появляется именно в существующем обычном чате Кати, не в другом чате, не в файле и не в почте.
- Если Катя отдельно одобрит Work-компромисс: один постоянный Work-чат в проекте, использующий контекст перенесённого музыкального чата; событие появляется в этом Work-чате.
- Не создаются новые чаты на каждое событие и не требуется ручное копирование.
- Повторная доставка не создаёт дубликаты; при отсутствии сети события сохраняются и отправляются после восстановления связи.
- Музыка и «Миры Магира» имеют независимые адресаты и очереди.
- Система честно сообщает о доставке/ошибке; «принято мостом» не выдаётся за «появилось в чате».
- До успешного теста на реальном целевом чате функция не считается готовой, а релиз 1.0 не объявляется полностью соответствующим требованию.
